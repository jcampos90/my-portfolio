module seam hand-copied fact deep module

Small and mostly well-shaped: one renderer per record type, content as pure data, a genuinely deep Section. The friction is not sprawl — it is hand-copied facts with nothing relating the copies, and one of them fails silently in front of the audience. Every count below came from grep over the source and the built out/index.html.

Status: candidate 1 has since been implemented — field contracts in components/sections/*.contract.ts, the check in test/portfolio-contract.test.mts, and docs/adr/0004-content-fields-declare-how-they-surface.md. The rest are still open.

1 · Join the content type to its renderer

components/sections/projects.tsx:3 (and about:1, experience:1, certifications:1, hero:3, header:1, contact:3) · content/projects.ts:14–24 · package.json:6–10

The section interface takes zero parameters. A test cannot substitute content, and the compiler cannot express “every field of Project appears on the page”.

A field can be populated for all three Featured projects, typecheck clean, and never reach the page. No test notices: there was no test.

after — one contract crossing content and page

content/*.ts

page + contracts
renders once
↓

test surface

the Portfolio's contract

  • every rendered field of every record appears
  • every record appears at least once
  • the prose in content/site.ts appears
  • the file at cvPath exists, source and build
  • out/ is newer than every source file

Shipped with no new dependency: node --test reads the content modules directly. Nine assertions, all green, and each gate was verified to fail when it should.

Problem. No invariant joined a content record's type to its renderer: sections create their own content dependency, so a field could exist in the data, typecheck clean, and never appear on the page.

Solution. A FieldContract<T> declared next to each renderer, enforced twice — by tsc, and by a check that reads the built page.

  • → the interface becomes the test surface
  • → data-present/page-wrong fails the build
  • → leverage: one render, all record invariants
  • → zero dependencies added

The tempting fix — pass content into each section as a prop — was rejected as a hypothetical seam: there is one content module per record type and nothing varies across it.

6 · Give the content records one closed set each

content/projects.ts:14–24 · components/sections/projects.tsx:24–38 · content/certifications.ts:19–20, 28–29 · app/layout.tsx:93

before — three states as two open optionals

repoUrl ✓
sourceNote ✗

Source link

repoUrl ✗
sourceNote ✓

“Source not published yet.”

repoUrl ✓
sourceNote ✓

note silently dropped

repoUrl ✗
sourceNote ✗

bare card, no source

Exclusivity exists only as render order — repoUrl ? link : sourceNote ? note : null. The type admits a fourth state with no meaning.

Same shape elsewhere: verifyUrl must end with credentialId (both halves hand-written twice) and that unchecked URL is published as structured data at layout.tsx:93. Four record types, four keying conventions: slug, a composite company-title string, credentialId, label — no identity field in the model.

after — a closed set, matched exhaustively

source: published

carries the repository url

source: unpublished

carries the note

Two states, one field, exhaustive match. The credential URL is derived from the id, so the two halves cannot disagree.

The styling seam already knows how to do this: button.tsx:13–24 and badge.tsx:9–12 model closed sets with literal unions, so a variant typo is a compile error. The content seam uses no unions at all.

Problem. A published source is one fact modelled as two independent optionals, and a credential URL must end with its own id — both invariants live in render order and in hand-typed strings, enforced nowhere.

Solution. One field carrying the source state, and a verify URL derived from the credential id.

  • → impossible states unrepresentable
  • → interface shrinks to one field
  • → a URL that can't 404 on a detail

7 · Dates that can be sorted, and one stated order

content/experience.ts:12, 18–52 · content/certifications.ts:6, 12–30 · components/sections/experience.tsx:9 · certifications.tsx:12

before — two conventions, opposite directions, both in the editor's head

experience.ts — newest first

Jan 2023 — Present

Mar 2020 — Dec 2022

May 2015 — Mar 2020

certifications.ts — oldest first

August 2026

September 2026

Both render in array order. Both date fields are display strings, so neither list can be sorted or validated. Nothing states the convention and the two modules disagree: reordering a role to fix a typo silently reorders the résumé.

after — one ordered value, order derived

one field per record

period: start + optional end · date: year + month

display text derives from it; order derives from it

sort → rendered order
format → label

One convention, stated and checkable. The cheap version is a comment naming the rule in each module; the good version is a field that carries the order.

Problem. The only fields with ordering semantics are display strings, and the two content modules order their lists in opposite directions with no stated rule, so a typo fix can silently reorder the résumé.

Solution. One order-bearing value per date, and a stated convention — or render order derived from the data.

  • → order stops being tribal knowledge
  • → sortable and checkable
  • → display text stays free-form

Deletion test — what earns its keep

Delete the module: does the complexity vanish (a pass-through), or reappear across N call sites (it earned its keep)?

lib/utils.ts → cn

1 line, 5 callers. Merge order reappears at each site if deleted. Earns its keep — small, not shallow.

components/section.tsx → Section

5 callers; hides the id ↔ id-heading ↔ aria-labelledby pairing. Deepest module in the tree.

components/section.tsx → Container

4 callers; owns the page width. Earns its keep, thinly.

components/ui/brand-icons.tsx

2.5 KB of SVG behind a 1-prop interface, 5 uses, documented as an adapter for lucide 1.x. The one clean element-level seam — the model for candidate 2.

components/ui/button.tsx → buttonClass

8 callers, so it earns its keep on usage — but ghost · link · lg · icon are declared and never selected. Interface 4× oversized.

components/ui/badge.tsx

1 caller passes variant="outline"; the default variant is unreachable. Pass-through — complexity vanishes.

components/ui/card.tsx

2 callers, but a card's surface is already defined by tokens in globals.css:34–35. Two homes for one visual fact. Borderline.

scripts/setup-cloudflare.sh

set_secret/set_var are defined and never called, so WRITTEN_SECRET can never fill. Inherited wizard library, marked “do not hand-edit”.

content/site.ts → links.businessSite

Zero consumers — since deleted rather than labelled structural, because a named consumer is what the contract requires.

Already well-shaped — do not touch

  • One renderer per record type. Five content modules, five section modules, clean 1:1 — the property most codebases this size get wrong.
  • Section is genuinely deep. A four-field interface hiding the section/anchor/heading pairing, the container, the spacing scale and the sticky-header offset.
  • Content modules are pure data. No JSX, no side effects — which is exactly what made the emitted output testable in candidate 1.
  • The ADRs are real, and so is the intent at the point of edit. content/projects.ts:1–12 and :69–78 record why a project has no link and why the Business site is absent.

top recommendation

Done: 1 · Join the content type to its renderer

It was the only defect where the failure was silent and reached the audience, and the cheapest to close: the content modules are pure data and the emitted page is already the real interface, so the contract needed no refactoring and no new dependency. It is now the detector for the whole family of hand-copied facts below it.
